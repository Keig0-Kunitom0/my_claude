# スペック駆動ドキュメントの作成

ステアリングドキュメントはAIエージェントが向かう先を指し示す「北極星」であり、実装の唯一の正となる。
各ドキュメントは `templates/` の雛形をベースに、以下の基準で作成する。

## 保存先（最初に確認する）
すべてのドキュメントは、`/implement-issue` が解決した**ステアリングディレクトリの絶対パス**の直下に置く。

- **`.claude/steering/...` を自分で組み立て直さない。** 呼び出し元から渡された絶対パスをそのまま使う。
- カレントディレクトリ起点の相対パス（`.claude/steering/...`）で書かない。リポジトリのサブディレクトリに
  `.claude/` があると、リポジトリルートではなくそちらに作られてしまう。
- 書き込み後、`ls -l <絶対パス>` で意図した場所に実在することを確認する。

## 共通の品質基準
- **断定的・定量的に書く**（「適切に」「検討する」などの曖昧語を避ける）。
- 構造化された技術要素（**コード例・メソッド名・Mermaid図**）を含めると、AIの指示追従性が上がる。
- ファイル名・行番号・クラス名など、参照先を具体的に書く。

## ステータス行（requirements / design / tasklist 共通・必須）
承認状態はドキュメント自身が持つ。3ドキュメントとも H1 の直下に**ステータス行**を置く。

```md
# Requirements: <タイトル>

**ステータス**: draft
```

- 作成時は `draft` とする。
- ユーザーが approve した時点で `approved（YYYY-MM-DD）` に更新する（日付は `date +%F` で取得する）。
- approve 後に内容を書き換えた場合は `draft` に戻し、再度 approve を得る。
- セッションをまたいだ再開時は、このステータス行だけを読んで「どのフェーズから再開するか」を判定する。
  そのため**ステータス行以外の場所に承認状態を書かない**（進捗ファイルを別途作らない）。

## メタ情報（requirements.md のみ・必須）
再開時に「どの issue の、どのブランチの作業か」を特定するための情報を、requirements.md の「メタ情報」セクションに永続化する。

```md
## メタ情報

| 項目 | 値 |
|---|---|
| Issue | https://github.com/<owner>/<repo>/issues/1234 |
| ブランチ | `1234/add-retry-to-webhook` |
| 派生元 | `abc1234` (origin/master) |
| PR | 未作成 |
```

- **作成時に必ず埋める**。Issue が無いチャット起点の作業では Issue 欄を「なし」とする。
- ブランチ名は**推測せず、実際に作成したブランチ名をそのまま書く**（再開時はこの値で `git switch` する）。
- **派生元は、ブランチを切った時点の SHA を書く**（括弧内に当時の記述を添える）。

  **なぜ SHA で残すか**: 派生元は既定でカレント HEAD であり、実行のたびに違う。
  記録しないと、再開時や最終セルフチェックで「どこからの差分を見ればよいか」が
  分からなくなる（作業ブランチ上でカレントを起点にすると差分が空になる）。
  ブランチ名だけだと後から動くため、**動かない SHA を唯一の情報源とする**。
- PR は作成されたら URL に更新する。未作成の間は「未作成」とする。
- メタ情報は requirements.md にだけ置く（design / tasklist には複製しない）。

## requirements.md — 何を・なぜ
テンプレート: `templates/requirements.md`
必須セクション:
- **背景**: なぜ必要か。解決する問題（問題の詳細・根本原因）。
- **変更・追加・削除する機能の説明**: 対象を表で列挙する（対象 / 場所 / 現状 / 変更後・用途）。
- **仕様**: 満たすべき振る舞いを断定的に箇条書きする。
- **スコープ外**: 今回やらないことと、その理由（スコープの肥大を防ぐ）。

## design.md — どう作るか
テンプレート: `templates/design.md`
必須セクション:
- **具体的な仕様・設計**: 現状の問題と解決方針。データフローや処理順は **Mermaid（sequence図 / ER図）** で図示する。設計詳細はコード例で示す。
- **実装アプローチ**: 手順（番号付き）、変更するコンポーネント（表）、既存パターンとの整合（表）、データ構造の変更（なければ「なし」と明記）、影響範囲の分析。
  - **既存パターンとの整合**: 新規追加する module / class / method / テスト / テーブル / カラムごとに、踏襲する前例を `path:line` で示す。
    プロダクト全体の一貫性を最優先し、設計方針・命名・書き方・粒度・テストの書き方を既存に揃える。
    前例が無い場合は「前例なし」と明記し、代わりに何に合わせるかを書く。
    踏襲元が Linter の閾値に抵触しているなど健全でない場合は、方針をユーザーに確認したうえで結論をここに書く。
- **動作確認対象**: 対象ごとに「○○で○○を確認する」と具体的な確認手順を書く。確認方法は画面操作・CLI実行・APIコール・ログ確認など対象に合わせ、可能な限り再現しやすい手順にする。

## tasklist.md — 具体的な実装タスク
テンプレート: `templates/tasklist.md`
ルール:
- チェックボックスは **1コミット相当の粒度**にする（例: 「○○メソッドの追加」「○○を○○に修正」）。
- 各チェックボックスの下に、対象ファイルと具体作業をネストする。**実装コード例**やテスト追加を含める。
- 作成後、requirements / design の要件を全て満たすかセルフチェックする。不足があればチェックボックスを追加する。
- 対応しないタスクは `→ **スキップ**（理由）` と明記する。

## decisions.md / blockers.md — 自走中の記憶（条件付き作成）
コンテキストウィンドウの自動圧縮で文脈が失われても、判断と詰まりを後から追えるようにするための記録。
**毎回作る必要はなく、該当する事象が起きたときにだけ追記する。**

- **decisions.md**（テンプレート: `templates/decisions.md`）: design.md に書かれていない設計判断・技術選定や、トレードオフのある選択を行ったとき、採用理由・代替案・影響とともに追記する。
  - **AI が自律的に下した判断と、ユーザーに確認して決まった方針の両方**を記録する（承認ループ中の確認・合意を含む）。決定者を明記する。
  - 決定内容は該当ドキュメント（requirements / design / tasklist）へ反映し、反映先を明記する。
  - issue の本文は複製しない（背景は requirements.md の「背景」、issue の URL は requirements.md の「メタ情報」に一本化する）。
- **blockers.md**（テンプレート: `templates/blockers.md`）: 実装が中断したとき、事象・再現条件・試したこと・原因・確認したいことを追記する。再開時は最初にこれを読む。
