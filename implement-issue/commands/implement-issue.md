## 概要
指定されたissueについて、要件定義 → 設計 → タスク分解 → 実装までを、
ユーザーと合意したドキュメント（requirements / design / tasklist）を唯一の正として自律的に進める。
レビューやPR作成はこのコマンドの範囲外とし、実装の完遂を目的とする。

重い読み込み（影響範囲調査・実装）はサブエージェントに委譲し、このコマンド自身はオーケストレーションに専念することで、
コンテキストウィンドウの消費を抑える。

## 前提・設定
`git` と GitHub CLI (`gh`) が使える環境で動作する。実行開始時に以下を各自の環境へ解決すること。

- **対象リポジトリ**: カレントディレクトリのリポジトリ（`gh repo view` で確認）
- **派生元** `<base>`: **既定はカレントの HEAD**。`--base <ref>` が渡された場合のみそれを使う。

  **デフォルトブランチを自動解決しない。** 派生元はその時々で違う（main/master のこともあれば
  develop、既存の作業ブランチのこともある）ため、**派生したいブランチに切り替えてから実行する**
  という明示的な行為を指定として扱う。別の起点にしたい場合のみ `--base` を渡す。

  worktree 内で実行される場合、カレントは呼び出し元が用意した位置になっている
  （detached HEAD のこともある）。`<base>` を checkout してはならない — 同じブランチを
  2箇所に checkout できないため、worktree では必ず失敗する。
- **リポジトリルート** `<root>`: **カレントディレクトリではなく、必ず次のコマンドの出力を使う。**

  ```sh
  git rev-parse --show-toplevel
  ```

  ステアリングの読み書きは**必ずこの出力を先頭に付けた絶対パス**で行う。
- **ステアリング格納先** `<steering>`: 次の順で解決する。**判定はすべて `<root>/` を前置した絶対パスで行う。**
  1. `<root>/.claude/steering/` が存在する → それを使う。
  2. 存在しないが `<root>/.claude/` が存在する → `<root>/.claude/steering/` を作成して使う。
  3. `<root>/.claude/` も存在しない → **勝手に作らず、`AskUserQuestion` で格納先をユーザーに確認する**
     （選択肢: `<root>/.claude/steering/` を新規作成 / `<root>/.steering/` を新規作成 / パスを指定）。
- **作業ディレクトリ**: `<steering>/<issue番号>-<タイトルのスラッグ>/`。
  既に同じ issue番号のディレクトリがある場合は**新規作成せず既存を再利用する**（ステップ0参照）。

### 保存先の絶対パス化（違反しやすい。必ず守る）
過去に、リポジトリのサブディレクトリから起動した際、そこに `.claude/` があったために
ステアリングが `<root>/<サブディレクトリ>/.claude/steering/` に作られる事故が起きている。次を厳守する。

- **`.claude` / `.claude/steering` を裸の相対パスで参照しない。** `ls .claude`・`mkdir -p .claude/steering`・
  `Write .claude/steering/...` はすべて禁止。存在確認・作成・読み書きのいずれも `<root>/` を前置する。
- **カレントディレクトリに `.claude/` があっても、それは判定材料にならない。** サブディレクトリの `.claude/`
  （`settings.local.json` などが置かれた作業用ディレクトリ）は `<root>/.claude/` とは別物である。
- **`cd` してから相対パスで書かない。** 作業ディレクトリを移動しても、ステアリングのパスは絶対パスのまま扱う。
- 解決した `<steering>` の絶対パスは、この後のステップとサブエージェントすべてで**同じ文字列をそのまま使い回す**
  （ステップごとに `.claude/steering` を組み立て直さない）。
- **テスト / Lint コマンド**: `CLAUDE.md` やプロジェクト設定（package.json / Makefile 等）から判定する。
  特定できない場合はユーザーに確認する。以降、サブエージェントにもこのコマンドを渡す。

`$ARGUMENTS` には issue番号・issueのURL・補足ドキュメントのパスのいずれか（複数可）を受け取る。
加えて次のオプションを受け取る。

| オプション | 意味 |
|---|---|
| `--context {パス}` | **前提知識**の指定（複数可）。扱いは「前提知識（`--context`）の解決」を参照 |
| `--base {ref}` | 作業ブランチの派生元。未指定ならカレントの HEAD |
| `--branch {名前}` | 作業ブランチ名を明示指定する。未指定なら既存の命名規約から推測する（ステップ1参照） |

## ステップ0: 再開判定（毎回、最初に実行する）
セッションをクリアした後に同じ issue を渡しても続きから再開できるよう、**着手前に必ず既存の作業状態を確認する**。

**先に `--context` を切り出す。** `$ARGUMENTS` に `--context {パス}` が含まれる場合、その値をすべて回収してから残りを issue の指定として解釈する（複数指定可）。回収したパスは「前提知識（`--context`）の解決」で扱う。

1. `$ARGUMENTS` から issue番号を解決する（URL の場合は末尾の数値が issue番号）。
2. 既存の作業を、上から順に探す。**`<root>` を必ず絶対パスで前置し、リポジトリ全体を対象にする**
   （過去に取り違えで `<root>/<サブディレクトリ>/.claude/steering/` に作られた分も拾うため）。
   1. `grep -rl "issues/<issue番号>" --include=requirements.md <root>`
      … requirements.md の**メタ情報**に記録された Issue URL で特定する（最も確実）
   2. `find <root> -type d -name "<issue番号>-*" -path "*steering*"`
      … ディレクトリ名で特定する（メタ情報が未記入の場合のフォールバック。旧配置の `<root>/.steering/` や
      サブディレクトリ配下も同時に拾える）
   3. `git branch --list "<issue番号>/*"`
      … ステアリングが未作成の場合（軽量フローで中断したケース）
3. **どれにも該当しなければ新規**。「前提・設定」に従って `<steering>` を解決してからステップ1へ進む。
4. **該当すれば再開**。ステップ1（ブランチ名の決定・作業ブランチの作成）は実行せず、以下を行う。
   0. 見つかった作業ディレクトリを**そのまま使う**（旧配置の `<root>/.steering/` や、取り違えで
      サブディレクトリ配下に作られたものであっても、勝手に移動しない）。ただし `<root>/.claude/steering/` の
      外にあった場合は、**その事実と実際のパスを1行でユーザーに伝える**（移動するかはユーザーが決める）。
   1. 見つかった `requirements.md` の**メタ情報**から作業ブランチ名を読み取り、`git switch <ブランチ名>` で戻る
      （メタ情報が無い場合のみ 2-3 で見つけたブランチを使う）。他ブランチへの checkout と `git pull` はしない。
   2. `requirements.md` / `design.md` / `tasklist.md` の**ステータス行のみ**を読み、下表で再開位置を判定する。
   3. `decisions.md` / `blockers.md` があれば読み、合意済みの方針と中断理由の文脈を復帰する。
   4. `git status --short` と `git log --oneline <派生元>..HEAD` で、未コミットの変更と完了済みコミットを確認する。
      **`<派生元>` はメタ情報に記録された SHA を使う。** 派生元は既定でカレント HEAD であり実行ごとに違うため、
      ここで再解決すると作業ブランチ自身を起点にしてしまい差分が空になる。
      メタ情報に派生元が無い（旧形式の）場合は `git log --oneline -20` で代替し、その旨を1行伝える。
   5. **再開位置・完了済みタスク・未コミット変更の有無**を1〜3行でユーザーに報告し、続行の合意を得てから該当ステップへ進む。

| ステアリングドキュメントの状態 | 再開位置 |
|---|---|
| `requirements.md` が無い、または `draft` | ステップ2 |
| `requirements.md` が `approved` で、`design.md` が無い、または `draft` | ステップ3 |
| `design.md` まで `approved` で、`tasklist.md` が無い、または `draft` | ステップ4 |
| 3ドキュメントとも `approved` | ステップ5（`tasklist.md` の未チェックの先頭タスクから） |

未コミットの変更がある場合は、内容を要約してユーザーに提示し、**活かして続けるか破棄するかを確認してから**進む（勝手に破棄しない）。

## 前提知識（`--context`）の解決

ステップ0 で回収した `--context` のパスを解決する。**ドメイン知識や仕様の前提を、利用者が明示的に持ち込むための入口である。**

**受け付けるのは任意の Markdown ファイルである。** スキル（`SKILL.md`）に限らず、プロジェクト固有の情報が書かれたドキュメントであれば何でも渡せる。

| 渡せるものの例 | 内容 |
|---|---|
| `docs/glossary.md` | 用語集・ドメインモデルの定義 |
| `docs/spec/billing.md` | 機能仕様書 |
| `docs/adr/0007-*.md` | 設計判断の記録（なぜその構造なのか） |
| `.claude/skills/*/SKILL.md` | スキルとしてまとめてある場合 |
| `README.md` / 社内ドキュメントのエクスポート | プロジェクトの前提が書かれたもの |

`.claude/skills/` などを**自動で読み込むことはしない。** 何が置かれているか予測できないものを実装の前提に採用すると、挙動が環境ごとに変わってしまうため。読ませたいものは利用者が明示的に指定する。

| 状態 | アクション |
|---|---|
| `--context` の指定が無い | 本ステップをスキップし、以降でも前提知識に言及しない |
| 指定されたパスが存在する | 絶対パスに解決し、`wc -l` で行数を取得する |
| 指定されたパスが存在しない | **エラーで止めず**、その旨をユーザーに1行で警告し、そのパスだけ除外して続行する |
| ディレクトリが指定された | 直下および配下の `*.md` を対象として展開する。**5ファイルを超える場合は展開せず**、その旨を警告してユーザーに個別指定を促す |

**拡張子で弾かない。** Markdown を想定しているが、テキストとして読めるものは受け付ける。ただしバイナリや極端に大きいファイルは、その旨を警告して除外してよい。

### 前提知識の使い方

- **500行以下は Read で全体を読む。500行超は全体を読まず、判断が必要になった観点を Grep で引く。**
- これは判定基準ではなく**事実の前提**である。要件・設計・実装を決めるための材料として使う
- **前提知識に反する実装をしてはならない。** 反する必要が生じた場合は、勝手に進めずユーザーに確認する
- **そこに書かれていないことを、書かれているかのように断定しないこと。** 前提知識は常に不完全である
- 前提知識を根拠に判断した場合は、requirements / design の該当箇所に「前提: {ファイル名} の {該当箇所}」を明記する
- 解決したパスは、`codebase-investigator` と `task-implementer` の**両方に渡す**

## ステップ1: issueの理解と作業ブランチの作成（新規時のみ）
1. `$ARGUMENTS` のissueを `gh issue view <issue番号> --comments` で読み込む（タイトル・本文・コメント全て）。
   ファイルパスが含まれる場合はその仕様書も読む。
2. 下記「作業ブランチ名の決定」に従ってブランチ名を決める。
3. 作業ブランチを切る。このコマンドではリモートへの push は行わない。

   ```sh
   git checkout -b <決定したブランチ名>              # --base 未指定（カレント HEAD から派生）
   git checkout -b <決定したブランチ名> <base>       # --base 指定時
   ```

   **`<base>` を checkout しない。`git pull` もしない。**
   カレントから派生するため checkout は不要であり、worktree 内では同じブランチを2箇所に
   checkout できず必ず失敗する。未コミットの変更がある状態でも落ちない利点もある。
   最新化するかは実行前にユーザーが決める。

4. 派生元を1行で報告する（承認は求めない。ブロックせず続行する）。

   ```
   <派生元の記述> (<短縮SHA>) から <新ブランチ> を切りました
   ```

   detached HEAD から派生した場合は `detached HEAD (abc1234) から ...` と書く。

   **この派生元 SHA を控えておき、ステップ2で requirements.md の「メタ情報」に記録する。**
   再開時と最終セルフチェックはこの値を差分の起点に使うため、ここで失うと後から復元できない。

### 作業ブランチ名の決定

**1. `--branch <名前>` が渡されていれば、それをそのまま使う**（推測しない）。

**2. 既存ブランチの命名規約から推測する。**

```sh
git for-each-ref --sort=-committerdate --format='%(refname:short)' refs/remotes/origin \
  | head -30 | sed 's|^origin/||' | grep -E '^[0-9]+'
```

- **`^[0-9]+` フィルタ**でノイズを除く。`master` / `main` / 環境ブランチ（`*-staging*` 等）/
  `revert-*` / 番号なしの実験ブランチは作業ブランチではないため、これで綺麗に落ちる
- **直近30本に限定する。** 古いブランチには現在使われていない規約が混ざっており、
  全期間を見ると現在の規約を見誤る
- 残ったものから判定する
  - **区切り文字**: `^[0-9]+([/_-])` の捕捉文字を多数決
  - **語の連結**: 区切り以降が `-` を含めば kebab-case、`_` を含めば snake_case
- **5本以上が同じ形なら採用**し、`<issue番号><区切り><タイトルのスラッグ>` を組み立てる

**推測が決めるのは「形式」だけで、「内容」は issue タイトルから作る。**

採用したら、聞かずに報告のみ行う。

```
既存ブランチの規約から 1234/add-retry-to-webhook を生成しました
（参考: 直近30本中28本が <番号>/<kebab> 形式）
```

**3. 判定できなければ `AskUserQuestion` でブランチ名を聞く。**
番号始まりのブランチが1本も無い、5本に満たない、形がばらけている場合が該当する。
**推測で押し切らない** — 外れたブランチ名は push 後に直しにくい。

**規約をハードコードしない理由**: このコマンドはプラグインとして配布されるため、
特定リポジトリの規約を焼き付けると他リポジトリで外れる。推測にすれば、規約を読み取れない
リポジトリでは自動的に「ユーザーに聞く」へ落ちて安全側に倒れる。

### 軽量フロー
**原則はステップ2〜5（重量級フロー）である。軽量フローは既定ではなく、次の条件を両方満たすときだけ選べる。**

1. 変更が**数行〜1ファイル程度**に収まり、設計判断の余地が実質無い（例: typo 修正、定数の値変更）。
2. **`AskUserQuestion` で「軽量フローで進めてよいか」をユーザーに確認し、明示的な同意を得た。**

**判断に迷ったら重量級フローを選ぶ。** ステアリングドキュメントが残らないことによる損失（再開できない・
レビューできない）のほうが、ドキュメント作成のオーバーヘッドより大きいためである。
条件を満たさないまま、ステップ2〜4を勝手に省略してはならない。

同意が得られた場合、ステップ2〜4のステアリングドキュメント（requirements / design / tasklist）作成と承認ゲート、およびステップ5のサブエージェント委譲を省略し、以下の最小手順で完遂する。
1. 影響範囲（参照箇所・依存関係）を確認し、結果をユーザーに簡潔に共有する。
2. 対応方針をユーザーに確認し、合意を得る（`AskUserQuestion` 等の利用を推奨）。
3. 実装し、テスト / Lint を通したうえでローカル commit する。
4. 実装完了をユーザーに報告する（レビューやPR作成は別途）。

軽量フローでも **禁止事項** と **原則**（`git push` をしない、既存仕様を勝手に変えない、失敗を握り潰さない）、および **前提知識（`--context`）の扱い**は重量級フローと同様に厳守する。

## ステップ2: requirements.md の作成
1. **最初に作業ディレクトリを絶対パスで作成し、作成先を検証する。** ファイルを書く前に必ず行う。

   ```sh
   # <root> は git rev-parse --show-toplevel の出力そのもの。相対パスにしない
   mkdir -p "<root>/.claude/steering/<issue番号>-<スラッグ>"   # <steering> がこれ以外に解決された場合はそのパス
   ls -d "<steering>/<issue番号>-<スラッグ>"                    # 実在を確認する
   ```

   出力されたパスが `<root>` 直下から始まっていない場合（例: `<root>/<サブディレクトリ>/.claude/...`）は**作成先を誤っている**。
   進まずに `<root>` を取り直してやり直す。以降のステップは、ここで検証した絶対パスだけを使う。
2. `implement-issue-spec-docs` スキルに従い、`<steering>/<...>/requirements.md` を作成する（ステータス行は `draft`）。
   **メタ情報**（Issue の URL / ステップ1で作成した作業ブランチ名 / PR）を必ず埋める。これが再開時の作業特定に使われる。
3. 書き込み後、`ls -l "<steering>/<issue番号>-<スラッグ>/requirements.md"` で**意図した絶対パスに実在すること**を確認する。
4. ユーザーにレビューを依頼し、**approveされるまで**ブラッシュアップする。
5. approve されたら**ステータス行を `approved（YYYY-MM-DD）` に更新**してから（日付は `date +%F` で取得）ステップ3へ進む。

## ステップ3: design.md の作成
1. 設計に着手する前に `codebase-investigator` サブエージェントを起動し、影響範囲と既存実装パターンの調査レポートを得る。**前提知識のパスがあれば渡す。**
2. `implement-issue-spec-docs` スキルと調査レポートに従い、`<steering>/<...>/design.md` を作成する（ステータス行は `draft`）。
3. ユーザーにレビューを依頼し、**approveされるまで**ブラッシュアップする。
4. approve されたら**ステータス行を `approved（YYYY-MM-DD）` に更新**してからステップ4へ進む。

## ステップ4: tasklist.md の作成
1. `implement-issue-spec-docs` スキルに従い、`<steering>/<...>/tasklist.md` を作成する（1コミット相当の粒度。ステータス行は `draft`）。
2. requirements.md / design.md の要件を満たすかセルフチェックし、不足を補う。
3. ユーザーにレビューを依頼し、**approveされるまで**ブラッシュアップする。
4. approve されたら**ステータス行を `approved（YYYY-MM-DD）` に更新**してからステップ5へ進む。

approve 済みのドキュメントを後から書き換えた場合は、ステータス行を `draft` に戻して再度 approve を得る。

## ステップ5: 実装
カレントが作業ブランチであることを確認し、**tasklist.md のチェックボックスを上から順に1つずつ** `task-implementer` サブエージェントに委譲する。

各チェックボックスについて:
1. `task-implementer` を起動し、以下を渡す。
   - 対象チェックボックスの番号と内容
   - ステアリングディレクトリの**絶対パス**（`<steering>/<issue番号>-<スラッグ>/`）
   - **前提知識のパス一覧**（`--context` の指定があれば。行数も添える）
   - テスト / Lint コマンド
2. レポートを受け取り、結果に応じて進める。
   - **成功**: 次のチェックボックスへ進む。
   - **対応方針の確認要求**: レポートに記載された確認事項をユーザーに伝え、方針の指示を仰いでから再開する。
   - **中断（5回試行しても失敗）**: 失敗箇所・再現条件・原因をユーザーに伝え、指示を仰ぐ。
3. 全チェックボックス完了後、**メタ情報に記録された派生元 SHA** との差分（`git diff <派生元>...HEAD`）が
   requirements / design / tasklist を満たすかセルフチェックする。
   不足があればユーザーに確認のうえ修正し、必要に応じて3ドキュメントも更新する。
4. 実装完了をユーザーに報告する（レビューやPR作成は別途行う）。

## 設計・実装方針: プロダクトの一貫性を最優先する
新しく **モジュール / クラス / メソッド / テスト / テーブル / カラム** を追加するときは、そのコード単体の最適さより
**プロダクト全体で読んだときの一貫性**を優先する。新規追加分だけを最適化すると、全体を俯瞰したときに設計思想や
書き方がばらつき、かえって可読性が下がるためである。

- **前例・類似機能がある場合**: 次を既存に揃える。design.md には踏襲元を `path:line` で明示する。
  - 設計方針（どの層に置くか・責務の切り方）
  - 命名（クラス名・メソッド名・ファイル名・テーブル名・カラム名）
  - 書き方（呼び出し方・エラーハンドリング・引数や戻り値の形）
  - クラス分割とテストの粒度
  - テストの書き方（アサーション / マッチャーの使い方、フィクスチャの用意の仕方）
- **前例が無い場合**: プロダクト全体の慣習から外れない形にする。近い層・近い役割のコードを参照し、
  「このプロダクトならこう書くはず」という形に寄せる。design.md に「前例なし」と、何に合わせたかを書く。

### 踏襲元が健全でない場合はユーザーに確認する
踏襲すべき前例が次のいずれかに当てはまるときは、**自分で判断せず** `AskUserQuestion` で方針を確認する。

- Linter / 静的解析の閾値に抵触している（例: RuboCop の `Metrics/ClassLength`・`Metrics/AbcSize`）
- Linter の除外リストに載せて違反を回避している（例: `.rubocop_todo.yml`）
- メタプログラミング等により、定義箇所やインターフェースが静的に追えない

提示する選択肢は次の3つとし、選ばれた方針に従う。

| 選択肢 | 内容 | 選ばれた後の扱い |
|---|---|---|
| 1. リファクタ先行 | 先に踏襲元をリファクタしてから機能を追加する | **今回のスコープが広がる**ため、requirements / design にリファクタ範囲を追記し、ステータス行を `draft` に戻して再 approve を得る |
| 2. 新規分のみ健全化 | 一貫性は多少損なうが、新規追加分は Linter に抵触しない設計にする | 判断と理由を `decisions.md` に記録する |
| 3. 別タスクに送る | 今回は既存に揃え、リファクタは今回のスコープ外とする | 判断と理由、リファクタすべき対象（`path:line` と該当ルール）を `decisions.md` に記録する。**issue の起票はこのコマンドでは行わず、ユーザーに委ねる** |

判断のタイミングは原則としてステップ3（design 作成時）。実装中に発覚した場合、`task-implementer` は自分で決めず
中断してレポートに確認事項を記載し、このコマンドがユーザーに確認する。

## 禁止事項
- **`git push` をしない。** このコマンドが行うのはローカルでの commit までとする（リモート反映・PR作成は範囲外）。
- **テストを通すためだけに既存の仕様を変更しない。** 既存箇所の仕様変更が必要な場合は、勝手に変更せず必ずユーザーに対応方針を確認する。
- **失敗を握り潰さない。** 原因が特定できないまま、テストの skip や期待値の安易な書き換えなど回避的な手段でテストを通さない。
- **issue を起票しない。** リファクタ等を別タスクに送る場合も、起票するかどうかと内容の判断はユーザーに委ねる
  （このコマンドの責務は指定された issue の実装に限る）。

## 原則
- **スペック駆動を厳守する。** 3ドキュメントに書かれた内容のみを実装する。
  やむを得ず逸脱する場合は必ずユーザーに報告し approve を得る。
- **途中再開**: セッションをクリアしても、同じ issue番号 / URL を `$ARGUMENTS` に渡せば**ステップ0の再開判定**で続きから再開できる。
  再開位置の判定は各ドキュメントの**ステータス行**、実装の進捗は `tasklist.md` の**チェック状態**を正とする（進捗を別ファイルに二重管理しない）。
  中断していた場合は `blockers.md`、合意済みの方針は `decisions.md` を先に読んで文脈を復帰してから再開する。
- **判断と詰まりの記録**（自動圧縮で文脈が失われないための保険。`implement-issue-spec-docs` スキルのテンプレート参照）。
  - `decisions.md`: 重要な設計判断・技術選定を行ったとき、決定者・採用理由・代替案・トレードオフ・反映先を追記する。
    AI が自律的に下した判断だけでなく、**ユーザーに確認して決まった方針**（ステップ2〜4の承認ループ中の合意を含む）も記録する。
  - `blockers.md`: 実装が中断したとき、事象・再現条件・試したこと・原因・確認事項を追記する。
