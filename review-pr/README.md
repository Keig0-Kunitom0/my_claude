# review-pr

PR を**11の専門サブエージェントに並列でレビューさせ**、結果を集約して Markdown に永続化する、[Claude Code](https://code.claude.com/docs) のプラグインです。再レビュー時は、**前回その指摘を出した観点だけ**を統括エージェントが選んで起動します。

```
/plugin marketplace add Keig0-Kunitom0/my_claude
/plugin install review-pr@my-claude
```

多くの観点を1つのコンテキストで順に確認していくと、後半の観点ほど注意が薄くなります。観点ごとに独立したサブエージェントへ委譲することで、**どの観点も等しくフレッシュな文脈で確認**されます。

> 親エージェントはレビューをしません。**対象の特定・情報取得・起動・集約・保存**に徹し、判断はすべて専門サブエージェントに委ねます。

## 特徴

- **並列レビュー**: 11観点を同時に走らせる。観点を増やしても待ち時間はほとんど変わらない。
- **増分レビュー**: 2回目以降は前回レビュー時点からの新規コミットだけを見る。コミットが増えていなければサブエージェントを1体も起動しない。
- **再レビューの絞り込み**: 指摘対応後の再レビューでは、`rereview-lead` が結果ファイルの `検出元` を見て、**前回その指摘を出した観点だけ**を起動する。自分が出した指摘を自分で検証するため、無駄な起動と重複が減る。
- **意図の理解**: PR と紐づく Issue を読み、背景 / 目的 / 対応方法を整理してから各エージェントに渡す。「目的未達」「過剰実装」「要件の対応漏れ」を判定できる。
- **結果の永続化**: **リポジトリルートの** `.claude/reviews/{ブランチ名}.md` に保存し、再実行時は上書きせず差分更新する。チェック済みの指摘は保持される。
- **規約の自動適用**: **リポジトリルートの** `.claude/rules/` にコーディング規約があれば検出し、変更ファイルにマッチしたものだけを渡す。規約違反は優先度が1段階上がる。
- **プロダクトへの特化**: 規約とドメイン知識を与えるほど、一般論ではなく**自分たちのプロダクトの基準**でレビューされる（[カスタマイズ](#カスタマイズプロダクトに特化させる)）。
- **移植性**: GitHub CLI (`gh`) ベースでリポジトリ非依存。デフォルトブランチも動的に取得し、特定の言語・フレームワークを前提にしない。
- **安全側の挙動**: 全サブエージェントが読み取り専用。レビュー結果のファイル以外は書き換えない。

### 向いているタスク / 向いていないタスク

| | 内容 |
|---|---|
| **向いている** | レビュー観点が多く、一人では見落としが出るPR |
| **向いている** | マージ前の最終確認。指摘を継続的に追跡したいPR |
| **向いている** | 長期間動いているブランチ。増分レビューで差分だけを追える |
| **向いていない** | 数行の軽微な修正。11体を起動するコストに見合わない |
| **向いていない** | 設計方針そのものの議論。これはレビューではなく対話で詰めるべき |

### 通常のレビュー依頼より優れている点

- **観点の網羅が構造的に保証される**。「今回は時間がないのでテストだけ見る」といった劣化が起きない。
- **確信度と重要度を分けて報告する**。「確信度は高いが些細」と「確信は中程度だが重大」を区別できる。
- **指摘が蓄積される**。同じ指摘が毎回積み上がることなく、未対応のものだけが残る。前回の指摘が解消されたかも判定する。

## 構成

このプラグインは1つのコマンドと11のサブエージェントで構成されます。

```
.claude-plugin/
└── plugin.json                        # プラグインの識別情報（name / version）
commands/
└── review-pr.md                       # 親コマンド（対象特定 / 起動 / 集約 / 保存を統括）
agents/
├── rereview-lead.md                   # 再レビューの統括（再レビュー時のみ）
├── design-review.md                   # 設計品質
├── reliability-review.md              # 堅牢性
├── test-review.md                     # テスト品質
├── performance-review.md              # 性能
├── comment-review.md                  # コメント・PR記述
├── surrounding-review.md              # 変更範囲外
├── best-practice-review.md            # 品質原則
├── typo-review.md                     # 誤字脱字
├── security-review.md                 # セキュリティ
├── api-review.md                      # API設計（条件付き起動）
└── database-review.md                 # DBスキーマ設計（条件付き起動）
```

スニペットのコメントは下表の「担当」に対応します。

| 名前 | 担当 | 具体的に見るもの | 起動 |
|---|---|---|---|
| `/review-pr:review-pr`（コマンド） | オーケストレーション | 対象特定 / PR・Issue の理解 / 起動 / 集約 / 保存。**レビューそのものはしない** | — |
| `rereview-lead` | 再レビューの統括 | 結果ファイルの `検出元` から起動対象を決めて観点エージェントを呼び出し、対応判定を集約。加えて**対応漏れ / スコープ外の混入 / 観点をまたぐ回避 / マッピングの誤り**を横断で検証 | **再レビュー時のみ** |
| `design-review` | 設計品質 | OOP原則、クラス・メソッドのサイズ、命名、不要コード、既存アーキテクチャとの整合性、新規型の設計（カプセル化 / 不変条件の表現） | 常時 |
| `reliability-review` | 堅牢性 | トランザクション整合性（ACID）、エラーハンドリング（サイレント失敗 / 過度に広い捕捉）、null ガードの過不足 | 常時 |
| `test-review` | テスト品質 | カバレッジの十分性、全分岐・全ステータスの網羅、テストの対称性、リグレッション（デグレ・機能削除） | 常時 |
| `performance-review` | 性能 | N+1、不要クエリ、JOIN の妥当性、メモリ、連打によるサーバー負荷 | 常時 |
| `comment-review` | コメント・PR記述 | コード内コメント（`NOTE:` / `TODO:` / docstring）の事実正確性と**過不足**、PR概要と実装の一致、PR上のコメントに埋もれた知見 | 常時 |
| `surrounding-review` | 変更範囲外 | 変更ファイルの**未変更部分**と、同一機能の周辺コード（1ホップまで）の不備。指摘は「別途対応推奨」に分離される | 常時 |
| `best-practice-review` | 品質原則 | コード品質ガイドライン（契約 / 抽象化レイヤー / モジュール化 / ユニットテストの原則）と、プログラミング原則ガイドライン（DRY・KISS・YAGNI、凝集度と結合度、7つの設計原理、コードの臭い） | 常時 |
| `typo-review` | 誤字脱字 | 実装コードと PR 記述のタイプミス | 常時 |
| `security-review` | セキュリティ | OWASP Top 10（認可バイパス / IDOR、インジェクション、機密情報の露出、認証・セッション管理） | 常時 |
| `api-review` | API設計 | RESTful 原則、URI 設計、ステータスコード、レスポンス設計 | API関連の変更があるとき |
| `database-review` | DBスキーマ設計 | 正規化、カラム名・型、制約、インデックス、エンティティ / イベントの分離 | スキーマ変更があるとき |

条件付きのものは、起動しなかった場合に「スキップ」と明示されます。**未起動と「指摘ゼロ」を区別できる**ようにするためです。

## 前提条件

- **Claude Code**（CLI / IDE 拡張のいずれか）
- **git**
- **GitHub CLI (`gh`)** … PR / Issue の読み込みに使用。認証済みであること。
- 対象が **GitHub でPRを運用しているリポジトリ**であること。

> PRが存在しないブランチでも、デフォルトブランチとの差分をレビューできます。

## 導入方法

### ステップ1: 前提ツールを確認・準備する

それぞれインストール済みか確認します。

```sh
claude --version   # Claude Code
git --version
gh --version
```

- **Claude Code** が未インストールの場合は [公式ドキュメント](https://code.claude.com/docs) の手順に従ってインストールしてください（CLI / IDE 拡張のいずれでも可）。
- **`gh`** が未インストールの場合は [GitHub CLI のインストール手順](https://github.com/cli/cli#installation) に従ってください（macOS なら `brew install gh`）。

次に `gh` を認証します。**この認証ができていないと PR を読み込めません。**

```sh
gh auth login          # ブラウザの指示に従って認証
gh auth status         # "Logged in to github.com" と表示されればOK
```

### ステップ2: プラグインをインストールする

Claude Code のセッション内で2コマンド実行するだけです。ファイルのコピーは不要です。

```
/plugin marketplace add Keig0-Kunitom0/my_claude
/plugin install review-pr@my-claude
```

インストール時にスコープを選べます。

| スコープ | 効果 | 向いている場面 |
|---|---|---|
| **User** | 自分のマシンの**全プロジェクト**で使える。各プロジェクトには何も置かない | 個人で複数リポジトリに使いたい（**推奨**） |
| **Project** | そのリポジトリの `.claude/settings.json` に記録され、チームで共有される | チーム全員に配りたい |
| **Local** | そのリポジトリで自分だけ | まず1つのリポジトリで試したい |

> 更新は `/plugin marketplace update my-claude` → `/reload-plugins` です。`plugin.json` の `version` が上がったときに配信されます。

### ステップ3: 認識されているか確認する

Claude Code を（再）起動し、新しいセッションで以下を確認します。

- プロンプトで `/review-pr:review-pr` がスラッシュコマンド候補に表示される
- `/plugin list` に `review-pr` が表示される

> サブエージェントは、コマンド実行中に必要なタイミングで自動的に起動されるため、手動での確認は不要です。

### ステップ4: 使う前の準備（任意）

そのままでも動作しますが、**プロジェクトのコーディング規約を用意しておくとレビュー精度が上がります**。

`.claude/rules/` に規約を置き、冒頭の `paths:` で適用対象を宣言してください。変更ファイルにマッチした規約だけが各サブエージェントへ渡されます。

```
{リポジトリルート}/.claude/rules/**/*.md   # プロジェクト固有
~/.claude/rules/**/*.md                    # ユーザー共通（全プロジェクトに適用）
```

規約ファイルの記載例:

```md
---
paths: /**/*.rb, /**/*.rake
---

# コーディング規約

- メソッドは20行以内に収める
- ...
```

`paths:` を書かない規約ファイルは、常に適用対象になります。

> 規約が500行を超える場合、全体を読み込まず必要な箇所だけを検索して参照します。大きな規約でもトークン消費が破綻しません。

## 使い方

```
# 全観点でレビュー（2回目以降は増分のみ）
/review-pr https://github.com/{owner}/{repo}/pull/123

# 増分判定を飛ばして全体を再レビュー
/review-pr https://github.com/{owner}/{repo}/pull/123 full

# 観点を絞る
/review-pr https://github.com/{owner}/{repo}/pull/123 test performance

# PR番号だけ、あるいは引数なし（カレントブランチから自動検出）
/review-pr 123
/review-pr

# プロジェクト固有のドキュメントを前提知識として読ませる（Markdown なら何でも可）
/review-pr 123 --context docs/glossary.md

# 複数指定・他のオプションとの併用もできる
/review-pr 123 full --context docs/glossary.md --context docs/spec/billing.md
/review-pr {URL} design --context .claude/skills/billing-domain/SKILL.md
```

### オプション一覧

引数はすべて**任意**で、**順序は問いません**。併用もできます。

| 引数 | 形式 | 説明 |
|---|---|---|
| **レビュー対象** | PR URL / PR番号 / ブランチ名 / **省略** | 省略時はカレントブランチから PR を逆引きします。PR が無い場合はデフォルトブランチとの差分をレビューします |
| **観点キーワード** | 下表のキーワード（複数可） | 指定した観点のエージェントだけを起動します。既定は `all` |
| `full` | — | 増分判定を飛ばして**全体を再レビュー**します。マージ直前の最終確認に使います |
| `--context` | `--context <パス>`（複数可） | **前提知識**として読ませる Markdown。ファイルでもディレクトリでも可。[詳細](#2-ドメイン知識は---context-で渡す) |

#### 観点キーワード

| キーワード | 起動するエージェント |
|---|---|
| `design` | `design-review` |
| `reliability` | `reliability-review` |
| `test` | `test-review` |
| `performance` | `performance-review` |
| `comment` | `comment-review` |
| `surrounding` | `surrounding-review` |
| `bestpractice` | `best-practice-review` |
| `typo` | `typo-review` |
| `security` | `security-review` |
| `api` | `api-review`（**自動判定を飛ばして強制起動**） |
| `database` | `database-review`（**自動判定を飛ばして強制起動**） |
| `all` | 上記すべて（**既定**）。`api` / `database` は変更内容を見て自動判定 |

#### `--context` について

渡したファイルは**全サブエージェントに前提知識として渡ります**。用語の定義や業務上の制約など、コードを読むだけでは分からない情報を補えます。

| 指定 | 挙動 |
|---|---|
| ファイル | そのファイルを前提知識として渡す |
| ディレクトリ | 配下の `*.md` を展開（**5ファイルを超える場合は展開せず**、個別指定を促します） |
| 複数指定 | `--context` を並べる |
| 存在しないパス | **エラーにせず警告**し、そのパスだけ除外して続行します |

### 増分レビュー

2回目以降は、**前回レビュー時点からの新規コミットだけ**を見ます。判定にはレビュー結果に記録した HEAD コミット SHA を使うため、コミット数では区別できない `amend` / rebase / force-push も検出できます。

| 前回からの状態 | 挙動 |
|---|---|
| コミットの追加なし | **サブエージェントを起動しない**（トークン消費ゼロ） |
| コミットが追加されている | 増分だけをレビューして追記 |
| 履歴が書き換わっている | フルレビューにフォールバック（その旨を明示） |

#### 再レビューは、指摘を出した観点だけが担当します

増分コミットは、前回の指摘を直したものであることがほとんどです。そのため再レビューでは、11体を一律に起動するのではなく、**`rereview-lead`（再レビュー統括エージェント）が起動対象を選びます**。

```
親コマンド
  └─ rereview-lead              ← レビュー結果ファイルの「検出元」を読む
       ├─ design-review         ← 指摘 #3 を出した本人
       ├─ test-review           ← 指摘 #5 を出した本人
       └─ security-review       ← 見逃しのコストが大きいため常に起動
```

1. レビュー結果ファイルから**未対応の指摘（`- [ ]`）とその `検出元`** を読み取る
2. **前回その指摘を出したエージェントだけ**を起動する。`security-review` は常に含め、API / スキーマを触っていれば `api-review` / `database-review` も加える
3. 各エージェントは、**自分が出した指摘だけ**を「解消されたか・妥当か・自分の観点で新たな問題が無いか」の観点で検証する
4. `rereview-lead` が判定を集約し、さらに**横断検証**（対応漏れ / スコープ外の混入 / 観点をまたぐ回避 / マッピングの誤り）を行う

自分が出した指摘を自分で検証するため、責任範囲が明確になり、重複した判定も出ません。11体すべてが全ファイルを読み直す無駄も無くなります。

> **待ち時間はほとんど変わりません。** サブエージェントは並列起動なので、体数を絞って効くのは**トークンコスト**です。
>
> **絞り込みには穴があります。** 前回指摘の無かった観点で修正が新たな問題を生んだ場合、その観点は起動されないため検出できません（`rereview-lead` の横断検証が部分的に埋めます）。**マージ直前には `full` で全観点を通す**ことを推奨します。

判定は4段階です。

| 判定 | 意味 |
|---|---|
| **解消** | 指摘の問題が正しく解消されている |
| **部分解消** | 一部だけ解消。残っている部分が示される |
| **未解消** | 変更はあるが、問題は残っている |
| **不適切** | 問題は消えたが、**回避的な手段**（テストの skip、例外の握り潰し、期待値の書き換え、条件の特例化）を使っている、または別の問題を生んでいる |

複数のエージェントの判定が割れた場合は、**最も厳しい判定が採用されます**。一体でも「不適切」と言えば不適切として扱い、そこから生まれた指摘は**優先度が1段階上がります**。一度指摘した問題が回避的に潰されている状態は、放置すると再発するためです。

結果はレビュー結果ファイルの「**前回指摘への対応状況**」セクションに記録され、再実行のたびに最新の判定で置き換えられます。

この仕組みは、各指摘に記録された **`検出元`** が支えています。重複してマージされた指摘は**全エージェント名が併記**され、次回の再レビューではその全員が起動されます。`検出元` が記録されていない旧形式の結果ファイルでは、安全側に倒して常時9体すべてを起動します。

> 増分レビューは、新しいコミットが差分外の既存コードを壊した場合に見逃す可能性があります。**マージ直前には `full` で一度通す**ことを推奨します。

## レビュー結果

```
{リポジトリルート}/.claude/reviews/{ブランチ名}.md
```

> **サブディレクトリから起動した場合も、保存先はリポジトリルートです。** 例えばリポジトリ内のサブディレクトリを作業ディレクトリとして起動し、そこに `.claude/` があっても、レビュー結果は `{リポジトリルート}/.claude/reviews/` に保存されます。コマンドは書き込み前に `git rev-parse --show-toplevel` を基点とした絶対パスでディレクトリを作り、保存先を検証します。`.claude/rules/` の探索も同様にリポジトリルートのみを対象とします。

に保存されます。ブランチ名に含まれる `/` などは `-` に置換されます。実行完了時に**絶対パスが出力される**ので、ターミナルからクリックして開けます。

```markdown
# PR #123 コードレビュー - 検索機能の追加

- **PR**: https://github.com/{owner}/{repo}/pull/123
- **ブランチ**: `feature-add-search`
- **レビュー済みコミット**: `a1b2c3...`
- **コミット数**: 7
- **レビュー日**: 2026-08-30

## PRの理解

**関連Issue**: https://github.com/{owner}/{repo}/issues/45

### 背景 / ### 目的 / ### 対応方法

## 変更ファイル

## 指摘事項

### Critical（P0） / High（P1） / Medium（P2） / Low（P3）
- [ ] **1. {タイトル}**
  **場所**: `{ファイル名}:{行番号}`
  **検出元**: {エージェント名}

## 前回指摘への対応状況

| 指摘番号 | 対応コミット | 判定 | 備考 |
|---|---|---|---|
| 3 | `a1b2c3d` | 解消 | |
| 5 | `e4f5g6h` | 不適切 | テストを skip して通している |

## 別途対応推奨
- [ ] **1. {タイトル}**
```

### 差分更新

同じブランチで再実行しても**上書きしません**。

- 既存の指摘は、チェック済み `- [x]` の状態も含めて保持される
- 新しい指摘だけが該当セクションの末尾に追加される
- 通し番号は既存の最大値の続きから採番される

### 「別途対応推奨」の分離

`surrounding-review` が見つけた**変更範囲外**の改善点は、本PRで対応すべき指摘とは分けて独立したセクションに記録されます。通し番号も独立しているため、本PRの対応漏れと混ざりません。別Issue化の検討材料として使えます。

## メタ情報

レビュー結果の冒頭には以下が記録されます。増分判定に使うため、**手で書き換えないでください**。

| 項目 | 用途 |
|---|---|
| `PR` / `PRタイトル` / `ブランチ` | 対象の識別 |
| **`レビュー済みコミット`** | **増分判定のキー**（40桁のフルSHA） |
| `コミット数` | 人間が読むための補助情報 |
| `レビュー日` | 最終レビュー日 |

## 確信度と重要度

各指摘には**確信度**（0-100）が付き、**80未満は報告されません**。誤検知でレビュー結果が埋まるのを防ぐためです。

加えて、一部のエージェントは独自の指標を返します。

| エージェント | 指標 |
|---|---|
| `test-review` | **重要度 1-10**（そのテストがどれだけ必須か） |
| `reliability-review` | **深刻度 CRITICAL / HIGH / MEDIUM** |
| `design-review` | 型設計の**4軸スコア**（カプセル化 / 不変条件の表現 / 有用性 / 強制） |

確信度は「その指摘が正しいか」、優先度は「直さないとどれだけ困るか」です。**確信度95の些細な命名ミスは P3、確信度85のデータ損失リスクは P0** になります。

## カスタマイズ（プロダクトに特化させる）

デフォルトのままでも観点は網羅しますが、**言えるのは一般論までです。** 「このプロダクトではこう書く」「この業務ではこれが正しい」を教えるほど、レビューは汎用ツールから**あなたのプロダクト専用のレビュアー**に変わります。

入口は2つ。**性質で使い分けます。**

| 与えるもの | 置き場所 | 渡り方 | エージェントの扱い |
|---|---|---|---|
| **規約・原則・プロダクト特有のルール** | `.claude/rules/` | 変更ファイルにマッチしたものが**自動で**全エージェントへ | **判定基準**。反していれば「規約違反」として指摘され、優先度が1段階上がる |
| **ドメイン知識・仕様の前提** | 任意の Markdown（仕様書 / 用語集 / ADR / `SKILL.md`） | `--context` で**明示的に**指定 | **事実の前提**。反していれば「仕様誤り」として指摘される |

### 1. 守らせたいルールは `.claude/rules/` に書く

各サブエージェントは、渡された規約のうち**自分の観点に関係する節を必ず確認**します。参照した規約はレポート末尾に列挙されるため、「どこまで見たか」も分かります。

ここに書くと効くもの:

- コーディング規約（命名、メソッドの長さ、エラー処理の書き方）
- チームで合意した設計原則
- **プロダクト特有のルール**（「この層から直接DBを触らない」「必ずこの共通メソッドを通す」「この列は論理削除で運用する」など）

書き方と `paths:` による絞り込みは[ステップ4](#ステップ4-使う前の準備任意)を参照してください。

> **レビューで毎回守らせたいことは、プロンプトで伝えるのではなく `.claude/rules/` に書いてください。** 口頭の指示はそのセッション限りで、次回のレビューには残りません。規約はファイルとして残り、チーム全員のレビューに効きます。

### 2. ドメイン知識は `--context` で渡す

**プロジェクト固有の情報が書かれた Markdown なら、何でも渡せます。** スキル（`SKILL.md`）である必要はありません。

```
# スキルにまとめてある場合
/review-pr 123 --context .claude/skills/billing-domain/SKILL.md

# プロジェクトのドキュメントをそのまま渡す
/review-pr 123 --context docs/glossary.md

# 複数指定もできます
/review-pr 123 --context docs/glossary.md --context docs/spec/billing.md
```

渡せるものの例:

| ファイル | 内容 |
|---|---|
| `docs/glossary.md` | 用語集・ドメインモデルの定義 |
| `docs/spec/*.md` | 機能仕様書 |
| `docs/adr/*.md` | 設計判断の記録（なぜその構造になっているのか） |
| `.claude/skills/*/SKILL.md` | 既にスキルとしてまとめてある場合 |

ディレクトリを渡すと配下の `*.md` が展開されます（5ファイルを超える場合は展開せず、個別指定を促します）。

指定したファイルは**全サブエージェントに前提知識として渡ります。**

`.claude/skills/` にあるスキルが**自動では読み込まれない**のは意図的です。何が置かれているか予測できないものをレビュー基準に採用すると、レビューの挙動が環境ごとに変わってしまうためです。読ませたいものは明示的に指定する方式にしています。

**渡す価値が高いのは、コードを読むだけでは絶対に分からない情報です。**

- 用語の定義（「契約」と「申込」は何が違うのか）
- 状態遷移のルール（`trial → active → suspended` は一方向、など）
- 業務上の制約（「解約後もデータは論理削除で残す」など）
- 権限・テナントの境界
- その構造を選んだ理由（ADR に書かれているような判断の経緯）

これが無いと、エージェントは「一般的にはこう書くべき」までしか言えません。渡してあれば、**仕様として間違っている実装**を指摘できるようになります。

> レビューのたびに読ませたいものが複数のドキュメントに散っている場合は、1つの Markdown にまとめておくと毎回の指定が楽になります。

> 前提知識は「違反を探す対象」ではなく「正しさを判定する材料」として渡されます。**そこに書かれていないことを、書かれているかのように断定しない**よう各エージェントに指示されています。
>
> なお、指定したファイルは全エージェントに渡るためトークン消費に効きます。500行を超える場合は、規約と同様に必要な箇所だけを検索して参照します。

### 3. 観点を絞って軽量に回す

全11体は大きなPR向けです。日常的には観点を絞ると軽く回せます。

```
/review-pr {URL} design reliability      # 設計と堅牢性だけ
/review-pr {URL} test                    # テストだけ
```

### 4. 特定のエージェントを常時外す

`commands/review-pr.md` の起動テーブルから該当行を削除すれば、そのエージェントは起動しなくなります。インストール済みのプラグインを直接編集するのではなく、フォークするか、後述のローカル読み込みで運用してください。

## 開発とリリース（メンテナ向け）

### ステップ1: リポジトリを clone する

```sh
git clone https://github.com/Keig0-Kunitom0/my_claude.git
cd my_claude
git switch -c feat/your-change
```

### ステップ2: ローカルのまま読み込んで動かす
**インストールせずに、作業ツリーの状態を直接読み込めます。** マーケットプレイスへの登録も push も不要です。

```sh
claude --plugin-dir /path/to/my_claude/review-pr
```

`--plugin-dir` にはプラグインルート（`review-pr/`）を渡します。**リポジトリルートではありません。** このリポジトリは複数のプラグインを収録しているため、ルートを渡しても読み込まれません。

セッション中に `.md` を編集したら `/reload-plugins` で再起動なしに反映できます。

```sh
# 認識状態の確認（別ターミナルから確認する場合も同じフラグが必要）
claude --plugin-dir /path/to/my_claude/review-pr plugin list
claude --plugin-dir /path/to/my_claude/review-pr plugin details review-pr
```

`plugin details` はコンポーネントの一覧と**トークンコストの見積もり**を表示します。サブエージェントを増やしたときの影響を確認できます。

> インストール実体は `~/.claude/plugins/cache/` 配下に展開されます。ここを直接編集しても更新で上書きされるため、改修は必ずこのリポジトリ側で行ってください。

### ステップ3: 修正する

修正後、**必ず `version` を上げてください。**

```jsonc
// review-pr/.claude-plugin/plugin.json
{
  "name": "review-pr",
  "version": "0.2.0",   // ← 上げる
  ...
}
```

> **version を上げないと、既にインストールしている利用者に更新が届きません。** プラグインは version 文字列でピン留めされ、上がったときにだけ配信されます。

`.claude-plugin/marketplace.json`（リポジトリルート）にも同じプラグインの `version` があります。**優先されるのは `plugin.json` 側**ですが、カタログの表示と食い違わないよう両方を揃えてください。

| ファイル | 役割 | 優先度 |
|---|---|---|
| `review-pr/.claude-plugin/plugin.json` | プラグイン自身の宣言 | **こちらが優先** |
| `.claude-plugin/marketplace.json` | カタログ上の表示情報 | plugin.json があれば無視される |

バージョンの上げ方の目安:

| 変更内容 | 上げ方 |
|---|---|
| サブエージェントの追加・削除、コマンドの手順変更 | マイナー（`0.1.0` → `0.2.0`） |
| レビュー観点の追記、文言修正 | パッチ（`0.1.0` → `0.1.1`） |
| README のみの修正 | 上げなくてよい（配信物に影響しないため） |

### ステップ4: 検証する

```sh
# マニフェストと、agents / commands / skills の構成を検証
claude plugin validate /path/to/my_claude

# CI では警告もエラー扱いにする
claude plugin validate /path/to/my_claude --strict
```

リポジトリルートを渡すと `marketplace.json` と両プラグインがまとめて検証されます。

### ステップ5: PR を作成してマージする

```sh
git add -A
git commit -m "feat: ..."
git push -u origin feat/your-change
gh pr create
```

**マージ先はデフォルトブランチ（`main`）です。** `marketplace.json` の source は `ref` を指定していないため、デフォルトブランチが参照されます。したがって **`main` にマージした時点で公開**されます。

```jsonc
// .claude-plugin/marketplace.json — ref 未指定 = デフォルトブランチ
"source": { "source": "github", "repo": "Keig0-Kunitom0/my_claude" }
```

> 安定版と開発版を分けたい場合は、`marketplace.json` の source に `"ref": "stable"` を指定し、`stable` ブランチにマージしたときだけ公開する運用にできます。

### ステップ6: 配信を確認する

利用者側（自分の環境でも）で取得します。

```sh
# CLI から
claude plugin update review-pr

# または Claude Code セッション内から
/plugin marketplace update my-claude
/reload-plugins
```

`claude plugin update` は**適用に再起動が必要**です。更新後、`/plugin list` に上げた version が表示されれば配信成功です。

### まとめ

```
git clone
  ↓
claude --plugin-dir /path/to/my_claude/review-pr で動作確認
  ↓
修正 + plugin.json の version を上げる（marketplace.json も揃える）
  ↓
claude plugin validate --strict
  ↓
PR 作成 → main にマージ = 公開
  ↓
claude plugin update review-pr（利用者側）
```

## 設計上のトレードオフ

- **トークン消費は増えます。** 複数のサブエージェントがそれぞれ変更ファイルを読むためです。並列実行なので体感時間はむしろ短くなりますが、大きなPRではコストが効いてきます。増分レビューはこれを緩和するための仕組みです。
- **観点をまたぐ洞察は出にくくなります。** 各エージェントは自分の担当範囲しか見ないため、「この設計だとN+1になる上にテストも無い」のような指摘は単独では出ません。親が集約時に拾います。
