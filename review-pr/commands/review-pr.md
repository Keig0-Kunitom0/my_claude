# PR Review（サブエージェント委譲版）

**引数**: `$ARGUMENTS`

レビュー観点を専門サブエージェントに分割し、**並列で**レビューさせた上で、その結果をあなた（親エージェント）が集約・重複排除してユーザーに提示し、ファイルに永続化する。

**あなた自身がコードレビューを行ってはならない。** 各観点の判断はサブエージェントに委譲し、あなたは対象特定・PR情報の取得・起動・集約・保存に徹すること。

**GitHubへのアクセスは `gh` コマンドを使う。** あなたが Step 3 で1回だけ取得し、その内容を各サブエージェントに渡す。サブエージェントに個別に GitHub を叩かせてはならない。

## 保存先の絶対パス化（違反しやすい。必ず守る）

`.claude/reviews/` と `.claude/rules/` は、**リポジトリルートのものだけ**を対象とする。リポジトリルートは次で解決する。

```sh
git rev-parse --show-toplevel   # 以下 <root>
```

- **`.claude` を裸の相対パスで参照しない。** `ls .claude/reviews`・`mkdir -p .claude/reviews`・
  `Write .claude/reviews/...`・`Glob .claude/rules/**/*.md` はすべて禁止。存在確認・作成・読み書き・探索の
  いずれも `<root>/` を前置した絶対パスで行う。
- **カレントディレクトリに `.claude/` があっても、それは判定材料にならない。** リポジトリのサブディレクトリ
  （例: `<root>/<サブディレクトリ>/`）を作業ディレクトリとして起動した場合、そこに `settings.local.json` などの入った
  `.claude/` が存在することがあるが、`<root>/.claude/` とは別物である。相対パスで書くと、レビュー結果が
  リポジトリルートではなくそちらに保存されてしまう。
- **`cd` してから相対パスで書かない。** 作業ディレクトリを移動しても、保存先は絶対パスのまま扱う。
- Step 2-1 で決定した絶対パスは、**Step 8 と Step 9 で同じ文字列をそのまま使い回す**
  （ステップごとに `.claude/reviews` を組み立て直さない）。

## Step 1: レビュー対象の特定

**目的**: owner / repo / PR番号 / ブランチ名 を確定する

**先に `--context` を切り出す。** `$ARGUMENTS` に `--context {パス}` が含まれる場合、その値をすべて回収してから残りをレビュー対象の指定として解釈する（複数指定可）。回収したパスは Step 3-5 で扱う。

| 引数の形式 | アクション |
|---|---|
| **PR URL**（`https://github.com/{owner}/{repo}/pull/{number}`） | URLをパースして owner / repo / PR番号 を取得する。この場合 `git remote` に依存しないため最も確実 |
| **PR番号のみ** | `gh pr view {N} --json url` で確認する（カレントリポジトリが対象） |
| **ブランチ名** | `git fetch` した上で、`gh pr list --head {ブランチ名} --json number,title,url` で紐づくPRを逆引きする |
| **未指定** | `git branch --show-current` でカレントブランチを取得し、同様に逆引きする |

PRが見つからない場合は、`gh repo view --json defaultBranchRef --jq .defaultBranchRef.name` でデフォルトブランチ名を取得し、`git diff {デフォルトブランチ}...HEAD` で差分を取得する。これを対象として続行する（この場合 PR番号は無し）。

**完了条件**: ブランチ名が確定していること（PR番号は存在すれば確定していること）

## Step 2: 既存レビュー結果の確認と増分判定

**目的**: 既にレビュー済みかを確認し、前回から何が増えたかを判定する

### 2-1. レビュー結果ファイルのパス決定

```
{git rev-parse --show-toplevel}/.claude/reviews/{サニタイズ済みブランチ名}.md
```

**ここで `git rev-parse --show-toplevel` を実際に実行し、絶対パスを確定させる。** 以降の Step 2-3 / 8 / 9 は、
この確定した文字列をそのまま使う（「保存先の絶対パス化」参照）。

**ブランチ名のサニタイズ**: `/` `\` `:` `*` `?` `"` `<` `>` `|` および空白・制御文字を `-` に置換する。置換後に連続した `-` は1つにまとめ、先頭末尾の `-` は除去する。

例: `feature/add-search:v2` → `feature-add-search-v2.md`

### 2-2. ファイルが存在しない場合

初回レビュー。そのまま **Step 3** へ進む。

### 2-3. ファイルが存在する場合

1. **Read ツールで読み込む**（Step 8 で再読込しないよう、内容を保持しておくこと）
2. 既存の指摘を「**未対応（`- [ ]`）**」と「**対応済み（`- [x]`）**」に仕分ける
3. ユーザーに一行で報告する
   例: `既存のレビュー結果を検出しました: 全12件（未対応 5件 / 対応済み 7件）`
4. メタ情報から `レビュー済みコミット` の SHA（以下 `PREV`）を読み取り、増分判定を行う

### 2-4. 増分判定

現在の HEAD を `git rev-parse HEAD` で取得（以下 `HEAD`）し、以下で分岐する。

| 条件 | 判定 | 挙動 |
|---|---|---|
| 引数に `full` が指定されている | 強制フル | 判定をスキップし**フルレビュー** |
| `PREV` が記載されていない（旧形式のmd） | 判定不能 | **フルレビュー**にフォールバック。以後 SHA を記録する |
| `PREV` == `HEAD` | **変更なし** | **Step 2-5 へ進み、そこで終了** |
| `git merge-base --is-ancestor {PREV} HEAD` が真 | **増分あり** | `git diff {PREV}..HEAD` を対象に**増分レビュー** |
| 同コマンドが偽 | **履歴が書き換わった**（rebase / force-push / amend） | 増分を安全に特定できないため**フルレビューにフォールバック**し、その旨をユーザーに明示する |

### 2-5. 「変更なし」の場合の終了処理

**サブエージェントを1体も起動しない。** 以下のみ出力して終了する。

- `前回レビュー時点からコミットの追加はありません。`
- 既存指摘のサマリ（全N件 / 未対応X件 / 対応済みY件）
- **Step 9 の保存先絶対パス出力**

**mdファイルは更新しない**（レビュー日も書き換えない。実質何もレビューしていないため）。

### 2-6. 再レビューの判定と生データの収集

既存のレビュー結果があり、かつ増分コミットがある場合、この回は**再レビュー**（前回の指摘への対応をレビューする回）である。

**増分コミットは前回の指摘への対応であることがほとんどである。** これを考慮せず差分だけをレビューすると、
「指摘した問題が本当に直ったのか」を誰も判定しないまま、新しい指摘だけが積み上がる。

再レビューでは、**`rereview-lead` サブエージェントが統括役として起動対象の決定と対応判定を行う**（Step 5）。
あなたはその判断材料となる生データを集めるだけでよい。

```bash
git log {PREV}..HEAD --format='%h %s'          # 増分コミットの一覧
git show {SHA} --name-only --format=''         # 各コミットの変更ファイル
```

**あなたが指摘とコミットの対応付けを結論してはならない。** ファイル名の一致だけで結び付けた推定は誤りやすく、
その検算も含めて `rereview-lead` の担当である。あなたが「解消した」と判断してもならない。

| 条件 | この回の扱い |
|---|---|
| レビュー結果が存在し、増分コミットがある | **再レビュー**（Step 5 で `rereview-lead` を起動する） |
| 初回レビュー | 通常レビュー |
| `full` 指定 / 履歴が書き換わってフルにフォールバック | **通常レビュー**（全観点を起動する。最終確認のため絞らない。ただし `quick` が併用されていれば `quick` の観点に絞る） |

**完了条件**: 初回 / 増分 / フル のいずれかが確定していること（再レビューの場合は増分コミットの一覧と変更ファイルも取得済みであること）

## Step 3: PR情報の取得とPR・Issueの理解

**目的**: サブエージェントに渡す共通コンテキストを組み立て、変更の意図を理解する

### 3-1. PR情報の取得（親が1回だけ実行する）

```bash
gh pr view {N} --json title,url,body,headRefName,baseRefName,state,author
gh pr diff {N}                 # フルレビュー時
gh pr diff {N} --name-only     # 変更ファイル一覧
git rev-list --count {baseRefName}..HEAD   # コミット数
git rev-parse HEAD                          # 記録用のフルSHA

# PR上のコメント（comment-review に渡す。他のエージェントには渡さない）
gh pr view {N} --json comments
gh api repos/{owner}/{repo}/pulls/{N}/comments --jq '.[] | {path, line, user: .user.login, body}'
```

`gh api` の `{owner}` / `{repo}` はカレントリポジトリから自動解決されるため、そのままの文字列で実行してよい。

**増分レビューの場合**は差分を `git diff {PREV}..HEAD` に差し替える。変更ファイル一覧も `git diff {PREV}..HEAD --name-only` を使う。

PRが存在しない場合は `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name` でデフォルトブランチ名を取得し、`git diff {デフォルトブランチ}...HEAD` で差分を取得する。PR由来の情報は省略する。

### 3-2. 紐づく Issue の特定

以下の順に探す。見つからなければ「関連Issueなし」として続行する。

| # | 手がかり | 探し方 |
|---|---|---|
| 1 | クローズキーワード | PR本文の `Closes #N` / `Fixes #N` / `Resolves #N`（変化形含む） |
| 2 | Issue参照 | PR本文の `#N` 形式の言及、Issue の完全URL |
| 3 | ブランチ名の数値 | 例 `1234/add-search` の `1234`。**Issue番号とは限らない**（チケット番号等の可能性）ため、`gh issue view` で取得して**内容が対応していることを確認できた場合のみ採用** |
| 4 | PRタイトルの数値 | 同上。確認できた場合のみ採用 |

```bash
gh issue view {N} --json title,url,body,state
```

複数の Issue が紐づく場合は全て読む。

### 3-3. 背景・目的・対応方法の整理

| 項目 | 内容 |
|---|---|
| **背景** | 何がきっかけでこの PR / Issue が生まれたのか |
| **目的** | 解決したい問題は何か |
| **対応方法** | どのようにして問題を解決しているのか（実装方針の大まかな要約） |

**情報が不足している場合の扱い（重要）**:

- PR本文もIssueも薄く背景や目的が読み取れない場合、**差分から推測してよいが、推測であることを必ず明示する**。該当項目に `（PR・Issueに記載がないため、差分からの推測）` と付記する
- **推測を断定的に書いてはならない。** 背景を創作すると、レビュー結果を後から読む人が誤った前提を持つことになる
- 全く判断材料がない項目は `（記載なし）` とする

### 3-4. 適用されるプロジェクトルールの検出

コーディング規約が置かれている場合、それを検出してサブエージェントに渡す。**プロジェクトの規約は、あなたやサブエージェントの一般知識より優先される。**

**探索先**（両方を見る。両方あれば両方対象）。**下表の絶対パスで探索し、裸の `.claude/rules/` で探さない**
（サブディレクトリの `.claude/rules/` を拾ってしまい、リポジトリの規約と取り違えるため）:

| 場所 | 用途 |
|---|---|
| `{git rev-parse --show-toplevel}/.claude/rules/**/*.md` | プロジェクト固有の規約 |
| `~/.claude/rules/**/*.md` | ユーザー共通の規約 |

どちらも存在しなければ本ステップはスキップし、以降の手順でもルールについて言及しない。

**変更ファイルとの突き合わせ**:

各ルールファイルの冒頭にある frontmatter の `paths:` を読み取り、Step 3-1 で取得した変更ファイル一覧と照合する。

```markdown
---
paths: /**/*.rb, /**/*.rake
---
```

- `paths:` の各グロブに**1つでも変更ファイルがマッチすれば、そのルールは適用対象**
- `paths:` が**無い**ルールファイルは、**常に適用対象**として扱う
- マッチするものが1つも無ければ、ルールは渡さない

**ルールファイルの中身は読まない。** 規約ファイルは数千行に及ぶことがあり、親が読むとコンテキストを圧迫する。**パスと行数だけを把握し、実際の読み込みは各サブエージェントに委ねる。**

行数は `wc -l` で確認し、Step 5 で渡す際の指示に使う。

### 3-5. 前提知識（`--context`）の解決

Step 1 で回収した `--context` のパスを解決する。**ドメイン知識や仕様の前提を、利用者が明示的にレビューへ持ち込むための入口である。**

**受け付けるのは任意の Markdown ファイルである。** スキル（`SKILL.md`）に限らず、プロジェクト固有の情報が書かれたドキュメントであれば何でも渡せる。

| 渡せるものの例 | 内容 |
|---|---|
| `docs/glossary.md` | 用語集・ドメインモデルの定義 |
| `docs/spec/billing.md` | 機能仕様書 |
| `docs/adr/0007-*.md` | 設計判断の記録（なぜその構造なのか） |
| `.claude/skills/*/SKILL.md` | スキルとしてまとめてある場合 |
| `README.md` / 社内ドキュメントのエクスポート | プロジェクトの前提が書かれたもの |

`.claude/skills/` などを**自動で読み込むことはしない。** 何が置かれているか予測できないものをレビュー基準に採用すると、レビューの挙動が環境ごとに変わってしまうため。読ませたいものは利用者が明示的に指定する。

| 状態 | アクション |
|---|---|
| `--context` の指定が無い | 本ステップをスキップし、以降でも前提知識に言及しない |
| 指定されたパスが存在する | 絶対パスに解決し、`wc -l` で行数を取得する |
| 指定されたパスが存在しない | **エラーで止めず**、その旨をユーザーに1行で警告し、そのパスだけ除外して続行する |
| ディレクトリが指定された | 直下および配下の `*.md` を対象として展開する。**5ファイルを超える場合は展開せず**、その旨を警告してユーザーに個別指定を促す |

**拡張子で弾かない。** Markdown を想定しているが、テキストとして読めるものは受け付ける。ただしバイナリや極端に大きいファイルは、その旨を警告して除外してよい。

**ここでも中身は読まない。** 規約と同様、パスと行数だけを把握し、読み込みは各サブエージェントに委ねる。

**完了条件**: 差分・変更ファイル一覧・コミット数・HEAD SHA・背景/目的/対応方法・適用ルール一覧・前提知識のパス一覧（指定があれば） が揃っていること

## Step 4: 起動するサブエージェントの決定

### 4-0. 再レビューの場合（最優先で判定する）

Step 2-6 で**再レビュー**と判定された場合、**起動するのは `rereview-lead` の1体だけ**である。
どの観点エージェントを起動するかは `rereview-lead` が決めて自分で呼び出す。あなたは観点エージェントを直接起動しない。

ただし引数に**観点キーワードが明示されている場合は、そちらを優先する**（ユーザーが観点を指定したのなら、その意図に従う）。
その場合は通常どおり 4-1 以降で起動対象を決め、`rereview-lead` は起動しない。

`api-review` / `database-review` の起動条件判定（4-2 / 4-3）は**再レビューでも実施し、判定結果を `rereview-lead` に渡す**。
修正で API やスキーマを触っていれば、前回の指摘が無くても見る必要があるため。

**`quick` が指定されていても `rereview-lead` は起動する**（`quick` は観点キーワードではなくモード指定であるため。4-1-1 参照）。
`quick` 指定の有無をそのまま `rereview-lead` に渡し、対象外エージェントの除外は `rereview-lead` 側で行わせる。

### 4-1. 引数によるキーワード指定

引数に観点キーワードが含まれる場合はそれに従う。**未指定の場合は該当する全エージェント**。

| キーワード | サブエージェント |
|---|---|
| `design` | `design-review` |
| `reliability` | `reliability-review` |
| `test` | `test-review` |
| `performance` | `performance-review` |
| `comment` | `comment-review` |
| `surrounding` | `surrounding-review` |
| `bestpractice` | `best-practice-review` |
| `api` | `api-review`（自動判定を飛ばして強制起動） |
| `database` | `database-review`（自動判定を飛ばして強制起動） |
| `typo` | `typo-review` |
| `security` | `security-review` |
| `all`（既定） | 常時9体 + 条件を満たせば `api-review` / `database-review` |

### 4-1-1. モード指定（`quick` / `full`）

`quick` と `full` は観点キーワードではなく**モード指定**である。**軸が異なるため併用できる。**

| 指定 | 軸 | 効果 |
|---|---|---|
| `full` | **どこを**見るか | Step 2-4 の増分判定を飛ばし、全差分を対象にする |
| `quick` | **誰が**見るか | 起動する観点エージェントを5体に絞る |

#### `quick`（簡易モード）

起動を次に絞る。**報告する優先度は絞らない**（P0〜P3 と「別途対応推奨」を通常どおり出す）。

| | エージェント |
|---|---|
| **起動する** | `design-review` / `reliability-review` / `test-review` / `security-review` / `typo-review` |
| **起動しない** | `performance-review` / `comment-review` / `surrounding-review` / `best-practice-review` |

`api-review` / `database-review` は `quick` でも**条件判定どおり起動する**（4-2 / 4-3）。スキーマと API の設計ミスはリリース後の修正コストが高く、簡易モードでも落とせないため。

**この5体を残す理由**:

| エージェント | 理由 |
|---|---|
| `security-review` | 見逃しのコストが他の観点と比べて非対称に大きい |
| `reliability-review` | データ損失・本番障害に直結する（P0 になりうる） |
| `test-review` | 落とすと「壊れたことに気づけない」状態になる |
| `design-review` | 構造の上に後続の変更が積み上がるため、後から直すコストが最も高い |
| `typo-review` | 差分を読むだけで判定でき、起動コストが小さい割に検出価値がある |

**落とした4体の見逃しを自覚すること。** とくに `performance-review`（N+1 / 連打によるサーバー負荷）は P1 相当の指摘を出しうる。`best-practice-review` の観点は `design-review` / `reliability-review` / `test-review` と重複しやすいため部分的には補われるが（6-1 の重複表を参照）、**`performance-review` を補うエージェントは無い。**

`quick` の用途は「作業中の PR に致命傷が無いかを速く確認する」ことである。**マージ直前の確認には使わない**（「運用上の注意」参照）。

#### 観点キーワードとの併用

観点キーワードが明示された場合は**そちらを優先し、`quick` は無視する**（ユーザーが観点を指定したのなら、その意図に従う）。無視した事実は Step 7 で1行報告する。

### 4-2. `api-review` の起動条件判定

Step 3 で取得した**変更ファイル一覧**を見て、以下のいずれかに該当すれば `api-review` を起動する。

| # | 判定条件 |
|---|---|
| 1 | パスに `api/` を含む（例: `app/controllers/api/...`） |
| 2 | ルーティング定義の変更（`routes` / `urls` / `*.routes.*` を名前に含むファイル、`config/routes*`） |
| 3 | シリアライザ・レスポンス整形（`serializers/`、`*serializer*`、`*.json.*` テンプレート、DTO / スキーマ定義） |
| 4 | GraphQL関連（`graphql/`、`*.graphql`） |
| 5 | OpenAPI / Swagger 定義（`openapi.yaml`、`swagger.yaml`、`*.openapi.*`） |
| 6 | コントローラの変更のうち、差分に `render json:` / `respond_to` / `head :` を含むもの |

**判定に迷う場合は起動する。** 起動しすぎるコストより、API設計の問題を見逃すコストの方が大きい。

### 4-3. `database-review` の起動条件判定

**テーブル構造そのものが変わる変更**を含む場合に起動する。差分の内容まで見て判定すること。

| # | 判定条件 |
|---|---|
| 1 | **テーブルの作成・削除**（`create_table` / `drop_table` / `CREATE TABLE` / `DROP TABLE`） |
| 2 | **カラムの追加・削除**（`add_column` / `remove_column` / `ALTER TABLE ... ADD` / `DROP COLUMN`） |
| 3 | **カラム名・テーブル名の変更**（`rename_column` / `rename_table` / `RENAME`） |
| 4 | **カラム型の変更**（`change_column` / `ALTER COLUMN` / `MODIFY`） |
| 5 | **制約の追加・削除**（`NOT NULL` / `UNIQUE` / 外部キー / `add_index` / `remove_index`） |
| 6 | マイグレーションファイルの追加（`db/migrate/`、`migrations/`、`*.sql` の DDL） |
| 7 | スキーマ定義ファイルの変更（`schema.rb` / `structure.sql` / `*.prisma` / ORM のモデル定義でカラムを宣言しているもの） |

**起動しないケース**:

- 既存テーブルへの**データ操作のみ**（`INSERT` / `UPDATE` / データ移行のみのマイグレーション）
- クエリの変更のみでスキーマに触れていない（それは `performance-review` の担当）
- `schema.rb` の変更が、他のマイグレーション適用に伴う**バージョン番号の更新だけ**の場合

**判定に迷う場合は起動する。** スキーマ設計の問題はリリース後の修正コストが高く、見逃すコストのほうが大きい。

**手動での強制指定**: 引数キーワード `database` を明示した場合は、上記判定に関わらず起動する。

起動を見送った場合は、Step 7 で `database-review: スキーマ変更が無いためスキップ` と明示する。

**完了条件**: 起動するエージェントの一覧が確定していること

## Step 5: サブエージェントの並列起動

### 再レビューの場合

**`rereview-lead` を1体だけ起動する。** 観点エージェントはあなたではなく `rereview-lead` が起動する。

渡すもの:

1. **レビュー結果ファイルの絶対パス**（Step 2-1 で決定済み）
2. 増分の差分（全文）と変更ファイルのパス一覧
3. **増分コミットの一覧**（SHA とコミットメッセージ。Step 2-6 で取得）
4. 背景 / 目的 / 対応方法（Step 3-3）
5. テスト / Lint コマンド（判明していれば）
6. 適用ルールのパスと行数（Step 3-4。あれば）
7. 前提知識のパスと行数（Step 3-5。あれば）
8. `api-review` / `database-review` の起動条件判定の結果（Step 4-2 / 4-3）
9. **`quick` 指定の有無**（4-1-1。指定があれば、除外対象は `rereview-lead` 側で落とさせる）

`rereview-lead` は起動対象を決めて観点エージェントを並列起動し、対応判定の集約と横断検証を行ったうえで
1つのレポートを返す。あなたはそのレポートを Step 6 で集約する。

**再レビューでは、以下の「通常レビューの場合」は実行しない。**

### 通常レビューの場合

**該当する全 Task を1つのメッセージにまとめて発行し、並列実行すること。** 逐次起動してはならない。

| サブエージェント（`subagent_type`） | 担当観点 | 起動 |
|---|---|---|
| `design-review` | OOP原則 / コードサイズ / 命名 / 必要最低限 / アーキテクチャ / **型設計（新規型がある場合）** | 常時 |
| `reliability-review` | ACID / エラーハンドリング / nullガード | 常時 |
| `test-review` | テストカバレッジ / リグレッション | 常時 |
| `performance-review` | パフォーマンス / 連打によるサーバー負荷 | 常時（**`quick` では起動しない**） |
| `comment-review` | コード内コメント / **PR概要** / **PR上のコメント** の正確性・完全性・長期的価値 | 常時（**`quick` では起動しない**） |
| `surrounding-review` | 差分**外**の周辺コードの不備・改善点 | 常時（**`quick` では起動しない**） |
| `best-practice-review` | `good_code_bad_code` / `principle_of_programming` に基づく品質 | 常時（**`quick` では起動しない**） |
| `typo-review` | 誤字脱字 | 常時 |
| `security-review` | セキュリティ | 常時 |
| `api-review` | API設計（RESTful原則 / URI / ステータスコード / レスポンス） | **条件付き**（Step 4-2。`quick` でも判定どおり） |
| `database-review` | DBスキーマ設計（正規化 / カラム名・型 / 制約 / インデックス / エンティティ・イベント） | **条件付き**（Step 4-3。`quick` でも判定どおり） |

### 各サブエージェントのプロンプトに必ず含めること

1. **Step 3 で取得した差分**（全文）
2. **変更ファイルのパス一覧**
3. **背景 / 目的 / 対応方法**（Step 3-3。意図が分かることで「目的未達」「過剰実装」「要件の対応漏れ」の判定が可能になる）
4. 「**親から差分が渡されているため、自分で GitHub から取得しないこと**」
5. 「**変更された各ファイルは Read ツールで実際に開いて確認すること**」（差分の前後関係とプロジェクト固有の記述スタイルを把握し誤検知を減らすため。**ファイルの中身は渡さない**）
6. 「確信度80未満の指摘は報告しないこと」
7. Step 2 で既存レビュー結果を読み込んでいる場合、**その指摘一覧**と以下の指示:
   - 既に指摘済みの内容は**再報告しない**
   - 「**未対応**」の指摘については、現在のコードで**解消済みかどうかを判定**し、解消されていれば「解消済み」として報告する

   > 前回の指摘への対応の妥当性判定は、**再レビュー時に `rereview-lead` が統括して行う**（Step 4-0 / Step 5）。
   > 通常レビューでこの項目に該当するのは、`full` 指定やフルレビューへのフォールバックで全観点を起動した場合である。

8. 増分レビューの場合はその旨（`{PREV}..HEAD` の範囲が対象であること）
9. **Step 3-4 で検出した適用ルールがある場合**、そのファイルパスと行数、および以下の指示:

   ```
   このプロジェクトには以下のコーディング規約が適用されます。
   これらはプロジェクトの規約であり、あなたの一般知識より優先されます。

   - {ルールファイルの絶対パス}（{行数}行）

   【読み込み方針】
   - 500行以下: Read ツールで全体を読み込むこと
   - 500行超: 全体を Read してはならない。レビュー中に判断が必要になった観点
     （命名、エラー処理、テストの書き方 等）について、Grep で該当セクションを
     引いて確認すること

   規約違反を見つけた場合は、指摘に「規約: {ファイル名} の {該当箇所}」を明記すること。
   ```

**500行超のルールを全体 Read させてはならない。** 規約ファイルは数千行に及ぶことがあり、最大11体が各自で全体を読むとトークン消費が破綻する。Grep での部分参照に倒すこと。

10. **Step 3-5 で解決した前提知識がある場合**、そのファイルパスと行数、および以下の指示:

    ```
    このレビューには以下の前提知識が指定されています。

    【これは判定基準ではなく前提知識です】
    - {前提知識ファイルの絶対パス}（{行数}行）

    - コードの正しさを判定するための事実として使うこと
    - ここに書かれていることに反する実装は「仕様誤り」として指摘してよい
    - ここに書かれていないことを、書かれているかのように断定しないこと
    - 読み込み方針は規約と同じ（500行以下は Read、超える場合は Grep で部分参照）

    前提知識を根拠に指摘する場合は、指摘に「前提: {ファイル名} の {該当箇所}」を明記すること。
    ```

**規約と前提知識は必ず別の枠で渡すこと。** 混ぜると、エージェントは前提知識に対しても「違反」を探しにいき、出力が歪む。

### `comment-review` にだけ渡す追加情報

- **PR概要の本文（全文）**。Step 3-3 で要約した背景/目的/対応方法ではなく、**PR本文そのもの**を渡すこと。要約では「概要の記述が実装と食い違っている」かどうかを判定できない
- **PR上のコメント一覧**（会話コメント・インラインコメント。発言者、対象ファイル、行番号、本文）
- PRが存在しない場合（デフォルトブランチとの差分をレビューする場合）は、この2つは渡さず、その旨を伝える

### `surrounding-review` にだけ渡す追加指示

- 対象は**差分そのものではなく**、変更ファイルの未変更部分および同一機能の周辺コード（**1ホップまで**）であること
- 差分内の問題は他エージェントが担当するため報告しないこと

**完了条件**: 起動した全サブエージェントのレポートが揃っていること

## Step 6: 結果の集約

**目的**: 各レポートを1つの一貫した指摘リストにまとめる

### 6-1. 重複のマージ（必須）

複数のサブエージェントが同じ問題を別角度から報告する。代表的な重複パターン:

| 重複しやすい組み合わせ | 例 |
|---|---|
| **`best-practice-review` × `design-review` / `reliability-review` / `test-review`** | 原則の適用範囲が重なるため**最も重複しやすい** |
| `reliability-review` × `security-review` | 例外の握り潰し、入力値の検証漏れ |
| `comment-review` × `design-review` | 命名と、それを説明するコメントの不一致 |
| `test-review` × `reliability-review` | エラー経路のテスト不足 |
| `api-review` × `design-review` | APIコントローラの責務 |

**マージのルール**:

1. **同一 `file:line` かつ同趣旨**の指摘は1件に統合する
2. 統合時は**確信度の高い方の記述を採用**し、他方が補足情報（隠れうるエラー、見逃されるバグ等）を持つ場合はそれを併記する
3. **`best-practice-review` / `api-review` の `根拠となる原則` は、マージ後も補足情報として必ず残す**（指摘の説得力の源であるため）
4. **`surrounding-review` の指摘が他エージェントの指摘と重複した場合は、`surrounding-review` 側を落とす**（差分に対する指摘の方が本PRで対応すべきものとして優先度が高い）
5. **`検出元` は、統合した全エージェント名を併記する**（1体に絞らない）。ルール4で指摘を落とした場合も、その検出元は併記に残す。
   再レビューでは**この `検出元` を見て起動するエージェントを決める**ため、ここを1体に丸めると、次回その観点が起動されなくなる

### 6-2. 観点をまたぐ洞察の補完

各サブエージェントは自分の担当観点しか見ていないため、**複数レポートを突き合わせて初めて見える問題**は集約時にあなたが拾うこと。例:

- 「N+1がある上に、その経路にテストも無い」
- 「新規追加されたクラスが既存と重複しており、かつ両者でエラーハンドリングの方針が食い違っている」
- 「実装が Issue に書かれた要件の一部を満たしていない」

### 6-3. 前回指摘への対応状況の確定（再レビュー時）

再レビューでは、判定の集約は既に `rereview-lead` が済ませている（最も厳しい判定を採用する規則も同エージェント側で適用済み）。
**あなたはその結果をそのまま採用する。判定をやり直さない。**

あなたが行うのは次の3点である。

1. `rereview-lead` の「横断検証」（対応漏れ / スコープ外の混入 / 観点をまたぐ回避 / マッピングの誤り）を、
   ユーザーへの提示とレビュー結果ファイルに反映する
2. **「不適切」と判定された対応から生まれた指摘は、優先度を1段階上げる。** 一度指摘した問題が回避的な手段で
   潰されている状態であり、放置すると再発するため
3. **「解消」と判定された指摘の通し番号を確定する。** これが Step 8-3 のルール11 で
   チェックボックスを `- [x]` に更新する根拠になる

通常レビュー（`full` 等）で各エージェントが個別に対応判定を返した場合は、**最も厳しい判定を採用する**。

```
解消 < 部分解消 < 未解消 < 不適切
```

**チェックを入れてよいのは「解消」だけである。** 「部分解消」「未解消」「不適切」は残作業があるため未対応のまま扱う。

### 6-4. 優先度の再分類

| 優先度 | 説明 |
|---|---|
| **Critical（P0）** | セキュリティ脆弱性、データ損失リスク、本番障害の可能性 |
| **High（P1）** | バグ、パフォーマンス問題、テスト不足 |
| **Medium（P2）** | 設計改善、リファクタリング推奨 |
| **Low（P3）** | スタイル、命名改善、コメント追加 |

**確信度と優先度は別軸である。** 確信度は「その指摘が正しいか」、優先度は「直さないとどれだけ困るか」。確信度95の些細な命名ミスは P3、確信度85のデータ損失リスクは P0。

**各エージェントが独自の重要度指標を返す場合は、それを優先度判定の主たる根拠とすること。**

| エージェント | 返す指標 | P0〜P3 への対応 |
|---|---|---|
| `test-review` | 重要度 1-10 | 9-10 → P0〜P1 / 7-8 → P1 / 5-6 → P2 / 3-4 → P3 |
| `reliability-review` | 深刻度 CRITICAL / HIGH / MEDIUM | CRITICAL → P0 / HIGH → P1 / MEDIUM → P2 |

`design-review` の**型設計評価（4軸スコア）は指摘ではない**ため、P0〜P3 に分類せず、Step 7 と保存時に独立した項目として扱う。

**プロジェクト規約（`.claude/rules/`）への違反は、一般論の指摘より優先度を1段階上げる。** 規約は明文化された合意であり、好みの問題ではないため。指摘には「規約: {ファイル名} の {該当箇所}」の記載を残すこと。

**前提知識（`--context`）に反する実装は「仕様誤り」として扱い、一般論の指摘より優先度を1段階上げる。** 実装の好みではなく、仕様との食い違いであるため。指摘には「前提: {ファイル名} の {該当箇所}」の記載を残すこと。

**`surrounding-review` の指摘は P0〜P3 の分類対象外**とし、別枠（「別途対応推奨」）で保持する。

**完了条件**: 重複が排除され、全指摘が P0〜P3 または「別途対応推奨」に分類されていること

## Step 7: レビュー結果をユーザーに提示

冒頭にサマリを付ける:

- 起動したサブエージェントと、それぞれの指摘件数
- **条件付きエージェントを起動しなかった場合はその旨を明示する**（未起動と指摘ゼロを区別するため）
  - `api-review: API関連の変更が無いためスキップ`
  - `database-review: スキーマ変更が無いためスキップ`
- **`quick` 指定の場合は、その旨と起動しなかった観点を明示する**（同じく未起動と指摘ゼロを区別するため）
  - `quick 指定のため performance / comment / surrounding / bestpractice をスキップ`
- **観点キーワードとの併用で `quick` を無視した場合はその旨**（4-1-1）
- 統合により何件が重複としてマージされたか
- P0〜P3 と「別途対応推奨」の件数内訳
- **前回指摘への対応状況**（再レビューの場合）。指摘番号ごとに 解消 / 部分解消 / 未解消 / 不適切 を提示する
- **再レビューで起動したエージェントと、起動しなかったエージェント**（`rereview-lead` のレポートより）。絞り込みが効いたことを可視化するため
- **横断検証の結果**（対応漏れ / スコープ外の混入 / 観点をまたぐ回避 / マッピングの誤り）

続いて優先度順（P0 → P3）に、各指摘を `場所（file:line）` / `指摘内容` / `推奨対応` / `検出元エージェント` とともに提示する。

最後に「**別途対応推奨**」を独立した見出しで提示する。

**完了条件**: ユーザーにレビュー結果が提示されていること

## Step 8: レビュー結果ファイルの保存

保存先とファイル名は **Step 2-1 で決定済み**のものを使う。

### 8-1. ディレクトリ作成と保存先の検証

Step 2-1 で確定した絶対パスを使い、書き込む前に作成と検証を行う。

```sh
mkdir -p "<root>/.claude/reviews"
ls -d "<root>/.claude/reviews"   # 実在を確認する
```

出力されたパスが `<root>` 直下から始まっていない場合（例: `<root>/<サブディレクトリ>/.claude/reviews`）は**保存先を誤っている**。
書き込まずに `<root>` を取り直してやり直す。書き込み後も `ls -l "<root>/.claude/reviews/{ファイル名}"` で
意図した絶対パスに実在することを確認する。

### 8-2. ファイルが存在しない場合 → 新規作成

下記テンプレートに従って新規作成する。

### 8-3. ファイルが既に存在する場合 → 差分更新

**Step 2-3 で読み込んだ内容を再利用すること。同じファイルを二重に Read しない。**

**上書きせず、以下のルールで差分更新する:**

| # | ルール |
|---|--------|
| 1 | 既存の指摘事項のタイトルと、今回のレビュー結果の指摘事項のタイトルを比較する |
| 2 | **既存ファイルに記載されていない新しい指摘事項のみ**を、該当する優先度セクションの末尾に追加する |
| 3 | 既存の指摘事項の**本文（タイトル / 場所 / 検出元 / 説明）は一切変更しない**。更新してよいのは**チェックボックスの状態だけ**で、その条件はルール11に従う |
| 4 | 通し番号は既存の最大番号の続きから採番する |
| 5 | 「別途対応推奨」セクションの通し番号は、P0〜P3 とは**独立して1から**採番する |
| 6 | メタ情報のうち **レビュー済みコミット / コミット数 / レビュー日 / 起動した観点** を更新する |
| 7 | **背景・目的は更新しない**（PRの目的は途中で変わらない前提）。**対応方法のみ**、増分コミットで実装方針に変化があった場合に追記する |
| 8 | 初回に `（差分からの推測）` としていた項目が、PR本文やIssueの加筆で確定情報になった場合は、推測の注記を外して更新してよい |
| 9 | 変更ファイルテーブルに新しいファイルがあれば追加する |
| 10 | **前回指摘への対応状況を判定した場合**、「前回指摘への対応状況」セクションを**最新の判定結果で置き換える**（追記ではなく毎回上書き。最新の状態だけが必要なため）。既存の指摘行の本文は、ルール3のとおり変更しない |
| 11 | **「解消」と判定された指摘（Step 6-3）は、チェックボックスを `- [ ]` から `- [x]` に更新する**（「別途対応推奨」セクションの指摘も同様）。「部分解消」「未解消」「不適切」は `- [ ]` のまま残す。**一度 `- [x]` にしたものを `- [ ]` に戻さない** |

**ルール11でチェックを入れる理由**: 再レビューは**未対応（`- [ ]`）の指摘の `検出元`** から起動対象を決める
（`rereview-lead` の手順1〜2）。解消した指摘にチェックが入らないと、**その観点が毎回起動され続け、
再レビューの絞り込みが機能しない。**

逆に、解消していない指摘にチェックを入れると次回その観点が起動されず**追跡が切れる**ため、
対象は判定が「解消」のものだけに限る。「前回指摘への対応状況」の表は**判定の履歴として従来どおり残す**
（チェックボックスは現在の状態、表は判定の根拠と経緯という役割分担）。

### 8-4. ファイル内容のルール

- **`検出元` には、その指摘を出した全エージェント名を記載する**（重複マージした場合は併記）。
  再レビューはこの欄を見て起動対象を決めるため、ここが欠けると次回その観点が起動されなくなる
- **`起動した観点` には、その回に実際に起動したエージェントを記録する。** `quick` や観点キーワードで絞った回は、
  指摘が無い観点が「きれいだったのか」「そもそも見ていないのか」を、後からファイルだけで区別できるようにするため
  （Step 7 で未起動を明示するのと同じ理由）
- Step 7でユーザーに提示した指摘事項をそのまま記載する
- 英語で出力された指摘事項は**日本語に翻訳**する
- **新規に追加する**指摘事項にはチェックボックス `- [ ]` を付ける（対応状況をトラッキングするため）。
  既存の指摘のチェック状態は 8-3 のルール11 に従って更新する

**完了条件**: ファイルが作成/更新され、内容がStep 7の結果と一致していること

## Step 9: 保存先パスの提示

レビュー結果の保存が完了したら、**応答の最後に保存先の絶対パスを出力すること。**

- **必ず絶対パス**で出力する（`git rev-parse --show-toplevel` の出力 + `/.claude/reviews/{ファイル名}`）
- 相対パス（`.claude/reviews/...`）や `~` 短縮形は**使わない**。ターミナルからクリックして開けなくなるため
- 他の文章に埋め込まず、独立した行に置く

出力例:

```
レビュー結果を保存しました:
/path/to/repo/.claude/reviews/feature-add-search.md
```

新規作成・差分更新のどちらの場合も出力する。**Step 2-5 の「変更なし」で終了する場合も出力する。**

## 使用例

```
/review-pr https://github.com/{owner}/{repo}/pull/1234
# 全観点でレビュー（2回目以降は増分のみ）

/review-pr https://github.com/{owner}/{repo}/pull/1234 full
# 増分判定を飛ばして全差分をレビュー

/review-pr https://github.com/{owner}/{repo}/pull/1234 quick
# 簡易モード（design / reliability / test / security / typo に絞る）

/review-pr https://github.com/{owner}/{repo}/pull/1234 quick full
# 全差分を対象にしつつ、観点は簡易モードに絞る（軸が違うので併用できる）

/review-pr https://github.com/{owner}/{repo}/pull/1234 test performance
# テストとパフォーマンスのみ

/review-pr https://github.com/{owner}/{repo}/pull/1234 api
# API観点のみ（自動判定を飛ばして強制起動）

/review-pr https://github.com/{owner}/{repo}/pull/1234 surrounding
# 周辺コードの改善点のみ

/review-pr 1234
# PR番号指定

/review-pr
# カレントブランチに紐づくPRを自動検出
```

## 運用上の注意

**増分レビューは差分外への影響を見逃しうる。** 新しいコミットが差分外の既存コードを壊した場合（例: メソッドのシグネチャを変え、呼び出し元が別ファイルにある）、壊れた側が差分に現れないため検出できない。`surrounding-review` が1ホップ分は補うが完全ではない。

**`quick` は観点を落とすぶん見逃しうる。** `performance-review` を補うエージェントが無いことに注意する（4-1-1）。

**マージ直前には `full` で、かつ `quick` を付けずに一度通すこと。** 増分と観点の両方を絞らない状態が、このコマンドで最も検出力が高い。

## 従来の `/review` との関係

`/review` は従来どおり単一コンテキストで15観点を通しで実行する。本コマンドはそれをサブエージェントに分割したもので、**両者は独立して並行運用される**。挙動に問題がある場合は `/review` を使用すること。

なお `/review` と `/review-pr` は**同一ブランチに対して同じファイル**（`.claude/reviews/{ブランチ名}.md`）を共有する。差分更新ルールにより両者の指摘が1ファイルに蓄積される。
